# GDR vs cudaMemcpy 基准测试结果

GPU 显存 ⇄ Host 内存 H2D / D2H 搬运路径对比。对比对象：

- **场景 A (GDR)**：RDMA loopback（QP 连到自身）+ GPUDirect RDMA，数据经 NIC 在 GPU 显存与 Host 内存间搬运。
- **场景 B (cudaMemcpy)**：`cudaMemcpyAsync` 直接走 PCIe DMA。

本文记录两轮测试：

1. **测试一（基线）**：单 NIC × 单 QP，RDMA WRITE。
2. **测试二（并发/READ）**：4 NIC × 2 QP = 8 lane 并发，分别测 RDMA WRITE 与 RDMA READ，验证 GDR 聚合带宽能否逼近 PCIe 上限。

---

## 综合分析

### 1. 多 NIC × 多 QP 并发显著提升 GDR 大包带宽，但仍未触及 PCIe 上限

| 配置 | GDR 大包带宽 (H2D) | 占 cudaMemcpy 比 | GDR 大包带宽 (D2H) | 占比 |
|------|-------------------:|----------------:|-------------------:|-----:|
| 单 NIC × 单 QP | ~26.4 GB/s | 0.46× | ~26.1 GB/s | 0.49× |
| 4 NIC × 2 QP   | **~40.1 GB/s** | **0.70×** | **~34.3 GB/s** | **0.64×** |

并发把大包带宽从 ~26 提升到 ~40 GB/s（H2D **+52%**），从 0.46× 拉到 0.70×，但**没有**达到 cudaMemcpy 的 ~57 GB/s。

### 2. 为什么 GDR loopback 逼近不了 PCIe DMA 上限

- **每字节过两次 PCIe**：loopback 路径下，H2D 时数据先 GPU→NIC（GPU PCIe egress），再 NIC→host（host/NIC PCIe）；而 `cudaMemcpyAsync` 是 GPU↔host 单次直连 DMA。GDR 对同一份数据产生约 2× 的 PCIe 流量。
  - 单 NIC ~26/57 ≈ 0.46，正好接近"减半"直觉。
  - 多 NIC 把 NIC 侧那一跳分散到不同 PCIe 通道/switch，于是聚合上去；但 **GPU 自身只有一条 x16 链路**，所有 NIC 对 GPU 的读/写最终都挤在 GPU 的这条 x16 上，成为新的瓶颈（≈ PCIe 上限），叠加 RDMA/loopback 开销后落在 ~40 GB/s。
- **D2H 比 H2D 低（34 vs 40）**：写显存（H2D 终点是 GPU）通常比读显存（D2H 源是 GPU）在 GDR 路径上更高效，cudaMemcpy 也呈同样趋势（57 vs 53）。

### 3. RDMA READ vs WRITE

- **大包基本一致**（H2D ~40、D2H ~34，两者持平）：说明大包瓶颈是 PCIe/loopback 结构，与 opcode 无关。
- **小包 WRITE 略优于 READ**：1 KB H2D WRITE 2.10 GB/s / 7.79 µs，READ 1.77 GB/s / 9.26 µs。READ 需要"请求→远端取数→返回"的往返，单边延迟更高；WRITE 是单向推送。**低时延小消息优先用 WRITE。**

### 4. 交叉点与选型建议

| 传输规模 | 推荐路径 | 理由 |
|----------|----------|------|
| ≤ 64 KB（小消息） | **GDR（WRITE）** | 时延/带宽 1.3–6× 优于 cudaMemcpy（后者有 ~40 µs launch 地板） |
| ~128–256 KB | 接近持平 | 交叉区（A/B ≈ 0.9–1.1） |
| ≥ 512 KB（大块） | **cudaMemcpy** | 直连 PCIe DMA，带宽是 GDR 的 1.4–2× |

---

## 结论

1. **多 NIC × 多 QP 并发是把 GDR 大包带宽往 PCIe 上限推的有效手段**：单卡单 QP ~26 GB/s → 4 卡 8 QP ~40 GB/s。
2. 但受 **GPU 单条 x16 PCIe 链路 + loopback 双跳** 的物理约束，GDR 大包带宽止步于直连 DMA 的 **~0.64–0.70×**，**无法真正逼近 PCIe 上限**。要进一步提升，唯有减少 loopback 跳数（真正的对端 RDMA 而非自环）或换更宽的 GPU 互联。
3. **opcode 对大包无影响**；小消息 WRITE 略优于 READ。
4. 工程取舍依旧清晰：**GDR 赢在小消息低时延，cudaMemcpy 赢在大块吞吐**——与 KVCache 传输里"GDR 适合 token 级小块、大块批量搬运用直连 DMA"的判断一致。
